# Автоматизация сервисного центра на Битрикс24

Прототип автоматизации дилерского автосервиса: приёмка и обслуживание автомобилей,
гараж клиента, контроль остатков запчастей и заявки на закупку.

## Архитектура

| Путь | Назначение |
|---|---|
| `local/App/Service/GarageService.php` | Гараж клиента: автомобили контакта, история ремонтов, поиск незакрытых заказ-нарядов |
| `local/App/Service/StockService.php` | Остатки запчастей, обмен с внешним сервисом, автозакупка, агент синхронизации |
| `local/App/Service/PurchaseService.php` | Заявки на закупку: создание, одобрение, отказ, уведомления |
| `local/App/Handler/GarageTabHandler.php` | Вкладка «Гараж» в карточке контакта (событие `crm:onEntityDetailsTabsInitialized`) |
| `local/App/Service/OrderService.php` | Заказ-наряд: состав запчастей из товарных позиций, автоматическое название |
| `local/App/Handler/DealControlHandler.php` | Контроль незакрытых заказ-нарядов и автоназвание (событие `crm:OnBeforeCrmDealAdd`) |
| `local/App/Handler/CarNamingHandler.php` | Название автомобиля «Марка Модель Госномер», агент синхронизации |
| `local/garage/tab.php` | Содержимое вкладки: карточки автомобилей |
| `local/garage/history.php` | JSON с историей обслуживания для всплывающего окна |
| `local/garage/create_order.php` | Приём автомобиля в ремонт из гаража в один клик |
| `local/garage/garage.js` | Всплывающее окно на `BX.PopupWindow` |
| `local/garage/garage.css` | Оформление гаража |
| `local/php_interface/init.php` | Регистрация обработчиков событий |

## Сущности

| Сущность | Тип | Идентификатор | Поля |
|---|---|---|---|
| Сервисное обслуживание | воронка сделок | `CATEGORY_ID = 1` | стадии: Приемка, Диагностика, Ожидание запчастей, Ремонт, Проверка, Завершено, Отказ клиента |
| Автомобили | смарт-процесс | `ENTITY_TYPE_ID = 128` | Марка, Модель, Госномер, Год, Цвет, Пробег, VIN, привязка к контакту |
| Заявки на закупку | смарт-процесс | `ENTITY_TYPE_ID = 129` | Запчасть, ID товара, Количество, Инициатор, Причина отказа, Автоматическая |
| Запчасти | каталог товаров CRM | инфоблок 14, раздел `spare_parts` | остаток в `QUANTITY`, цена в базовом типе |
| Сделка | доработка | - | `UF_CRM_DEAL_CAR` (привязка к автомобилю, тип `crm`), запчасти в товарных позициях |

Автомобили и заявки хранятся в смарт-процессах, поэтому доступны через REST
для интеграции с внешними системами.

## Процессы

### Гараж клиента
1. В карточке контакта появляется вкладка «Гараж» (обработчик события карточки CRM).
2. Вкладка показывает карточки автомобилей: марка, модель, госномер, год, цвет, пробег.
3. По клику открывается окно с заголовком «Название автомобиля - Номер (Имя клиента)»
   и историей обращений: название, дата создания, стадия, ответственный со ссылкой на
   профиль, сумма, список запчастей.

### Контроль незакрытых заказ-нарядов
При создании заказ-наряда система ищет незавершённые сделки по тому же автомобилю.
Если такая есть, создание отменяется, ответственный получает уведомление,
пользователю показывается причина отказа.

### Остатки и автозакупка (агент)
Агент `\App\Service\StockService::syncAgent()` раз в сутки опрашивает внешний сервис
`random.org`, который возвращает текущее количество запчасти на складах.
Если сервис вернул `0`:
1. создаётся заявка на закупку 10 единиц,
2. остаток устанавливается в 10,
3. заявка закрывается со статусом «Выполнено»,
4. закупщику уходит уведомление, что запчасть кончилась и закуплено 10 штук.

Обмен пишется в журнал `local/logs/stock_sync.log`.

### Заявки на закупку вручную
1. Сотрудник (например менеджер) создаёт заявку с запчастью и количеством.
2. Заявку согласует закупщик; если активных закупщиков нет, заявка уходит
   начальнику отдела закупок.
3. При одобрении остаток увеличивается на указанное количество, заявка переходит
   в «Выполнено», инициатор получает уведомление.
4. При отказе указывается причина, остаток не меняется, заявка переходит
   в «Отклонено», инициатор получает уведомление с причиной.

## Применённые модули курса

| Модуль курса | Где применён в проекте |
|---|---|
| Инфоблоки и каталог товаров | Запчасти в каталоге CRM, раздел `spare_parts`, остатки и цены, товарные позиции заказ-наряда |
| D7 ORM и работа с данными | `TypeTable`, `Service\Container`, фабрики смарт-процессов, `UserTable`, типизированные сервисы |
| События и обработчики | Вкладка карточки CRM, контроль незакрытых заказ-нарядов, регистрация в `init.php` |

## Приём автомобиля в ремонт

Кнопка «Принять в ремонт» в гараже создаёт заказ-наряд с заполненными клиентом,
автомобилем, названием и стадией «Приемка», после чего открывает его карточку.
Стандартная форма создания сделки не переносит значения пользовательских полей
из адреса, поэтому заказ-наряд создаётся серверным сценарием, а контроль
незакрытых заказов срабатывает штатным обработчиком события.

## Технические нюансы

- Пользовательские поля смарт-процесса создаются для владельца, который возвращает
  `Factory::getUserFieldEntityId()` (он опирается на ID типа, а не на `ENTITY_TYPE_ID`).
  После создания полей нужен сброс кеша, иначе ORM их не видит.
- Смарт-процессы занимают диапазон `ENTITY_TYPE_ID` 128-191.
- Автозакупка пополняет склад один раз: нужное количество проставляется операцией одобрения заявки.
- Смарт-процессы в этой сборке не публикуют события сохранения элемента, поэтому
  название автомобиля синхронизирует агент `\App\Handler\CarNamingHandler::syncAgent()`.
- Госномер входит в название автомобиля: так в селекторе заказ-наряда различаются
  одинаковые модели разных клиентов.
- Запчасти вынесены в отдельный раздел каталога: агент остатков не должен затрагивать
  прочие товары портала.
- Сотрудники входят в группу «Моя компания: Сотрудники», иначе портал закрывает доступ.
- Все тексты вынесены в языковые файлы, у методов описан PHPDoc, используется D7 API,
  управляющие конструкции оформлены по PSR-12, ядро продукта не изменялось.
