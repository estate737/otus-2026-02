# Автоматизация сервисного центра на Битрикс24

Прототип автоматизации дилерского автосервиса: приёмка и обслуживание автомобилей,
гараж клиента, контроль остатков запчастей и заявки на закупку.

> Ветка `final-project` содержит только файлы проектной работы. На учебном портале
> `local/php_interface/init.php` общий с домашними заданиями, поэтому в ветку вынесены
> только регистрации проекта. Инструкция для сотрудников - `USER_GUIDE.md`.

## Сущности

| Сущность | Тип | Идентификатор | Поля |
|---|---|---|---|
| Сервисное обслуживание | воронка сделок | `CATEGORY_ID = 1` | стадии: Приемка, Диагностика, Ожидание запчастей, Ремонт, Проверка, Завершено, Отказ клиента |
| Автомобили | смарт-процесс | `ENTITY_TYPE_ID = 128` | Марка, Модель, Госномер, Год, Цвет, Пробег, VIN, привязка к контакту, наблюдатели |
| Заявки на закупку | смарт-процесс | `ENTITY_TYPE_ID = 129` | состав в товарных позициях; Инициатор, Причина отказа, Создана автоматически, Решение обработано |
| Запчасти | каталог товаров CRM | инфоблок 14, раздел `spare_parts` | остаток в `QUANTITY`, цена в базовом типе |
| Сделка | доработка | - | `UF_CRM_DEAL_CAR` (привязка к автомобилю, тип `crm`), запчасти в товарных позициях |

Автомобили и заявки хранятся в смарт-процессах, поэтому доступны через REST
для интеграции с внешними системами (`crm.item.*`).

## Процессы

### Гараж клиента
1. В карточке контакта появляется вкладка «Гараж» (обработчик события карточки CRM).
2. Вкладка показывает автомобили: марка, модель, госномер, год, цвет, пробег
   и текущее состояние: свободен или в ремонте с указанием стадии.
3. По клику открывается окно с заголовком «Название автомобиля - Номер (Имя клиента)»
   и историей обращений: название, дата создания, стадия, ответственный со ссылкой на
   профиль, сумма, список запчастей.
4. Вкладка и окно истории показывают только то, что сотрудник может открыть по правам CRM:
   механик видит автомобили и заказ-наряды, где он ответственный, менеджер и директор - все.

### Приём автомобиля в ремонт
Кнопка «Принять в ремонт» создаёт заказ-наряд с заполненными клиентом, автомобилем,
названием и стадией «Приемка» и открывает его карточку. Стандартная форма создания
сделки не переносит значения пользовательских полей из адреса, поэтому заказ-наряд
создаётся серверным сценарием, а контроль незакрытых заказов срабатывает штатным
обработчиком события. Принять в ремонт можно только доступный сотруднику автомобиль.
Менеджер передаёт заказ-наряд механику, назначая его ответственным.

### Доступ механика к клиенту и автомобилю
Роль механика открывает записи, где он ответственный, а клиенты и автомобили закреплены
за менеджерами. Когда механика назначают ответственным за заказ-наряд, обработчик
`WorkOrderAccessHandler` добавляет его в наблюдатели клиента и автомобиля. Права CRM
уровня «Свои» открывают запись наблюдателю, поэтому механик видит клиента и машину
из своих заказ-нарядов и не видит остальных.
- Доступ передаётся только к записям, которые может открыть сотрудник, сохранивший
  заказ-наряд: подставив в свой заказ-наряд чужой автомобиль, механик доступа к нему
  не получит.
- Если роль уже открывает запись (менеджер, директор), наблюдатель не добавляется.

### Контроль незакрытых заказ-нарядов
При создании заказ-наряда система ищет незавершённые сделки по тому же автомобилю.
Если такая есть, создание отменяется, ответственный получает уведомление,
пользователю показывается причина отказа. Проверка живёт в событии, поэтому
работает для карточки, гаража, робота и REST одинаково.

### Остатки и автозакупка (агент)
Агент `\App\Service\StockService::syncAgent()` раз в сутки опрашивает внешний сервис,
который возвращает текущее количество запчасти на складах. Если сервис недоступен
или ответил не числом, остаток не изменяется, в журнал пишется отказ.
Если сервис вернул `0`:
1. создаётся заявка на закупку 10 единиц,
2. заявка переводится в «Выполнено», обработчик решения пополняет остаток до 10,
3. закупщику уходит уведомление, что запчасть кончилась и закуплено 10 штук.

Обмен пишется в журнал `local/logs/stock_sync.log`.

### Заявки на закупку вручную
1. Сотрудник создаёт заявку в карточке и выбирает запчасти из каталога
   в разделе «Запчасти».
2. Событие `onCrmDynamicItemAdd_129`: система называет заявку по составу, назначает
   согласующего (закупщик, если все закупщики отсутствуют - начальник отдела закупок),
   переводит заявку «На согласовании» и уведомляет согласующего.
3. Решение закупщика - смена стадии. Событие `onCrmDynamicItemUpdate_129`:
   - «Выполнено»: остатки увеличиваются на количество из заявки, инициатор
     получает уведомление;
   - «Отклонено»: причина отказа обязательна, остатки не меняются, инициатор
     получает уведомление с причиной.
4. После решения заявка получает признак «Решение обработано», поэтому повторные
   сохранения склад не пополняют.

## Права доступа

| Роль | Заказ-наряды | Клиенты и автомобили | Заявки на закупку | Роль каталога |
|---|---|---|---|---|
| Механик | свои | из своих заказ-нарядов | свои | «Механик сервисного центра» (просмотр товаров) |
| Менеджер | все | все, гараж клиентов | все, изменение своих | «Менеджер по продажам» |
| Закупщик, начальник отдела закупок | нет | нет | все, решение сменой стадии | «Кладовщик» |
| Директор | все | все | все | «Директор» |

- Роли CRM задают матрицу прав по сущностям, включая переход между стадиями.
- Выбор запчастей в карточках требует права каталога «Просмотр товаров», поэтому
  сотрудники привязаны к ролям каталога.
- Раздел сделок у сотрудников сервиса сразу открывает воронку «Сервисное обслуживание»,
  у закупщиков в левом меню есть пункт «Заявки на закупку».

## Технические нюансы

- События сохранения смарт-процессов. ORM-события таблицы элементов (`crm_items_N::OnAfterUpdate`)
  при работе через операции CRM не срабатывают. После сохранения ядро отправляет события
  модуля `crm` через `Service\Operation\Action\SendEvent`: `onCrmDynamicItemAdd`, `onCrmDynamicItemUpdate`
  и их варианты с номером типа, например `onCrmDynamicItemUpdate_129`. В событие передаются
  `item` и `id`. На этих событиях построены согласование заявок и название автомобиля.
- Обработчик заявок сам сохраняет заявку, что снова порождает событие. Повторный вход
  блокирует статический флаг обработчика, а признак `UF_CRM_PR_PROCESSED` исключает
  повторное выполнение решения.
- Автозакупка и ручное одобрение проходят один путь: перевод в «Выполнено»
  и обработчик решения, поэтому склад не пополняется дважды.
- Обязательность причины отказа задана атрибутом поля на стадии «Отклонено»
  (`FieldAttributeManager`, scope `category_9`). Операция смарт-процесса проверяет
  стадийные поля по сортировке стадий: при одинаковой сортировке диапазон «от Отклонено
  до Отклонено» накрывает все стадии, и поле становится обязательным везде. Стадиям
  заявок задана сортировка 10-50 в порядке процесса.
- Права на смарт-процесс без воронок задаются на его категорию по умолчанию. Элементы
  «Автомобилей» лежат в категории 8, и ядро проверяет права по сущности `DYNAMIC_128_C8`;
  запись `DYNAMIC_128` без категории при проверке элемента не используется.
- Наблюдатель получает в атрибутах прав записи код `CU<ID сотрудника>`, и уровень роли
  «Свои» открывает ему запись. У смарт-процесса наблюдатели включаются настройкой типа
  `IS_OBSERVERS_ENABLED`.
- Поиск товара в карточке CRM (`ProductProvider`) проверяет право каталога `catalog_read`.
  Роли CRM его не дают: без роли каталога поиск запчастей пуст.
- Раздел сделок открывает воронку из опции сотрудника `crm / current_deal_category`.
  Без неё открывается «Общая воронка», к которой у ролей сервиса нет доступа.
- Пользовательские поля смарт-процесса создаются для владельца, который возвращает
  `Factory::getUserFieldEntityId()` (он опирается на ID типа, а не на `ENTITY_TYPE_ID`).
  После создания полей нужен сброс кеша, иначе ORM их не видит.
- Смарт-процессы занимают диапазон `ENTITY_TYPE_ID` 128-191.
- Уведомления по заявке отправляются с тегом `SERVICE_PURCHASE|<ID>`: так они
  группируются и при необходимости удаляются.
- Госномер входит в название автомобиля: так в селекторе заказ-наряда различаются
  одинаковые модели разных клиентов.
- Запчасти вынесены в отдельный раздел каталога: агент остатков не затрагивает
  прочие товары портала.
- Сотрудники входят в группу «Моя компания: Сотрудники», иначе портал закрывает доступ.
- Все тексты вынесены в языковые файлы, у методов описан PHPDoc, используется D7 API,
  управляющие конструкции оформлены по PSR-12, ядро продукта не изменялось.
